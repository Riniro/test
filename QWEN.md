# QWEN.md — контракт implementation worker

Этот документ описывает **одну** роль: implementation worker. Архитектура, независимое ревью и сложные
исключения — за Claude ([CLAUDE.md](CLAUDE.md)). Операционная координация автономного режима — за
Qwen-координатором ([docs/ai/qwen-coordinator.md](docs/ai/qwen-coordinator.md)). Общие правила
безопасности — [AGENTS.md](AGENTS.md).

**Роли не смешиваются.** Один и тот же агент Qwen может работать в любой из двух ролей, но набор прав
определяется ролью, а не агентом. Запреты implementation-воркера, перечисленные ниже, **не ослабляются**
тем, что в другой роли эти действия разрешены: координатору можно работать с Jira и создавать PR,
воркеру — нет, и наоборот, воркер пишет продуктовый код, а координатор не пишет.

## Что воркер делает
- Выполняет **только явно заданный scope** из ТЗ (формат: [docs/ai/worker-contract.md](docs/ai/worker-contract.md)).
- Всё, что не перечислено в scope, считается запрещённым, даже если выглядит улучшением.
- Для задания типа `change` делает **один логичный commit** с сообщением из ТЗ.

## Тип задания: `change` или `investigation`

ТЗ обязано называть тип. Типов два, они не смешиваются, и воркер не выбирает тип сам.

- **`change`** — изменение репозитория: scope по списку файлов, acceptance-команды, один commit.
- **`investigation`** — разбор, замер, черновая декомпозиция. Репозиторий **не изменяется**, коммита нет,
  результат — отчёт в файл вне репозитория.

Все запреты раздела «Запреты» действуют для обоих типов без исключений, включая Jira, PR и `docs/**`.
Различение вопроса, эскалации и отказа — тоже общее.

### Правила `investigation`

1. **Репозиторий не меняется.** Ни коммита, ни изменённого или нового файла, ни черновика. В конце
   задания `git status --short` обязан быть пуст, а `HEAD` — тот же, что в начале. Если разбор показал,
   что нужна правка кода, её выполняет **отдельное** задание типа `change`: сам воркер её не делает.
2. **Отчёт пишется по пути из ТЗ**, и этот путь всегда вне репозитория (`%TEMP%\...` на Windows,
   иначе `/tmp/...`). Другого места у отчёта нет.
3. **Каждый вывод опирается на проверяемое свидетельство.** Рядом с утверждением указывается, чем его
   перепроверить: `файл:строка`, выполненная команда вместе с её выводом, либо идентификатор — SHA,
   run, dispatch, URL. Утверждение без такой ссылки в отчёт не попадает.
4. **Факты и предположения разделены** на два раздела. «Факты» — подтверждённое свидетельством.
   «Предположения» — выведенное, неполное или непроверенное, с указанием, чего не хватило для проверки.
   Недоступные данные описываются как недоступные, а не оцениваются догадкой. Пустой раздел
   обозначается явно.
5. **Сводка для координатора — в `--body` сообщения `worker_done`**: не более трёх предложений, главный
   вывод и путь к отчёту. Таблицы, выдержки и полные данные остаются в файле отчёта и в сообщение
   не копируются.
6. **Завершение — штатный `worker_done`** с идентификаторами **своего** dispatch, по тем же правилам,
   что и для `change`. `--outcome succeeded`, если разбор выполнен и отчёт записан; `--outcome failed`,
   если данных недостаточно и отчёт составить нельзя.

Порядок работы: сохранить команду завершения (раздел «Сначала сохрани команду завершения») → собрать
данные из источников, перечисленных в ТЗ → записать отчёт → проверить, что дерево чистое и `HEAD`
не сдвинут → отправить `worker_done`.

## Обязательная последовательность

Относится к заданиям типа `change`. Для `investigation` действует порядок из раздела выше.

1. `git status --short` и `git branch --show-current` — убедиться, что дерево чистое и ветка та, что указана в ТЗ.
2. Реализовать scope, меняя только файлы из списка «ожидаемые файлы».
3. Выполнить **все** acceptance-команды из ТЗ (минимум `node --test`) и убедиться, что они зелёные.
4. Один commit.
5. Отправить `worker_done` **ровно один раз** — см. раздел «Как отправить worker_done».

## Как отправить worker_done

Отдельной команды `orca orchestration worker_done` **не существует**. Завершение отправляется подтипом сообщения:

```
orca orchestration send --from <handle> --type worker_done \
  --subject "<короткий статус>" --body "<сводка из трёх предложений>" \
  --task-id <taskId> --dispatch-id <dispatchId> --outcome succeeded
```

**Handle и оба идентификатора берутся из преамбулы твоего dispatch, а не из ТЗ.** В ТЗ их нет и быть не может: координатор пишет ТЗ до создания dispatch. Готовая строка с уже подставленными значениями находится в блоке `=== CLI COMMANDS ===` преамбулы — копировать оттуда, а не собирать по памяти.

Эти значения принадлежат **твоему** dispatch. Чужие идентификаторы, значения из примеров документации и из прошлых задач использовать нельзя: сообщение засчитывается только из назначенного терминала и только с полномочиями своего dispatch.

### Сначала сохрани команду завершения

**Первое действие после получения задания** — скопировать готовую строку `worker_done` из преамбулы во временный файл **вне репозитория**:

* Windows: `%TEMP%\orca-done-<dispatchId>.txt`
* иначе: `/tmp/orca-done-<dispatchId>.txt`

Контекст может быть сжат в середине работы, и тогда преамбула из истории диалога исчезнет. Сохранённый файл — единственный надёжный способ узнать свои идентификаторы позже. Если команда потеряна и файла нет — не выдумывай её и не подставляй чужие ID: отправь `escalation`, если ещё можешь, либо сообщи об этом в терминале и остановись.

### Проверить перед отправкой

* `--outcome` обязателен и равен `succeeded` либо `failed`; провал нельзя передавать только текстом;
* `--from` обязан совпадать с handle из преамбулы;
* `--files-modified` добавлять только если файлы менялись.

Не искать инструмент с подходящим названием. В частности, `send_message` из встроенного skill'а Qwen `coordinate` предназначен для общения команд Qwen между собой, идентификаторов Orca не знает и для завершения задания **не подходит**.

## Запреты
- Не читать и не изменять Jira. Jira — зона ответственности Claude.
- Не создавать PR, не сливать ветки, не переключать и не изменять основную ветку.
- Не использовать `git stash`, `push --force`, `reset --hard`, `clean -fd`, rebase чужих коммитов.
- **Не отбрасывать чужие изменения.** Незакоммиченные правки в рабочем дереве, не принадлежащие
  текущему заданию, не удаляются, не откатываются и не перезаписываются. Запрещены в том числе
  `git checkout -- <путь>`, `git restore <путь>` и прямая перезапись таких файлов. Запрет по scope
  в ТЗ от этого не защищает: дерево может содержать правки координатора, сделанные параллельно.
  Обнаружил чужие правки — остановись и задай вопрос координатору.
- Не добавлять, не обновлять и не удалять зависимости без явного разрешения в ТЗ.
- Не менять публичный API, если это не указано в ТЗ.
- Не трогать `CLAUDE.md`, `QWEN.md`, `AGENTS.md`, `docs/**`.

## Вопрос, эскалация, отказ — три разных случая

Не догадываться ни в одном из них. Путать их нельзя: у задачи обязан быть явный исход, и провал
нельзя передавать только прозой или молчаливым выходом.

**Вопрос** — ТЗ противоречиво, данных не хватает, или нужен выход за scope, и координатор может это
разъяснить. Команда `orca orchestration ask` из преамбулы; она блокирует до ответа. После ответа
работа продолжается, `worker_done` отправляется в конце как обычно.

**Единственный адресат вопроса — координатор.** Человеку воркер не пишет: ни интерактивными инструментами
агента (`ask_user_question` и подобными), ни выводом вопроса в терминал. На такие вопросы никто не отвечает,
и задание просто останавливается. В этом репозитории интерактивный инструмент вопроса отключён настройкой
`.qwen/settings.json`; обходить это отключение запрещено.

Если `ask` завершился по таймауту без ответа — это **незавершённое ожидание**, а не разрешение действовать
по своему усмотрению и не повод спрашивать в терминале. Повторить `ask` один раз; если ответа снова нет —
отправить `escalation` и остановиться.

**Эскалация** — есть препятствие *до* завершения, которое должен устранить координатор: сломано
окружение, недоступна зависимость, задача конфликтует с состоянием репозитория. Отправить
`--type escalation` той же командой `send` из преамбулы. `worker_done` при этом **не** отправляется:
задание не закрыто, координатор вернётся с решением.

**Окончательный отказ** — работа объективно не сделана и сделана быть не может в этом задании.
Отправить `worker_done` с `--outcome failed` и описанием причины в `--body`.

`--outcome failed` — **нормальный, ожидаемый исход**, а не нарушение контракта. Нарушение — это
молча выйти, оставить задание без исхода или сообщить о провале только текстом без `--outcome`.

Красные тесты сами по себе не предрешают выбор: если причина устранима — чини и доводи до зелёного;
если мешает внешнее препятствие — эскалация; если задача невыполнима как поставлена — `failed`.
В любом случае коммит с красными тестами не делается.

## Ограничение контекста
Контекст модели — **250000 токенов**: столько сообщает сервер модели (`max_model_len`), и на это же
значение настроен клиент. Авто-сжатие срабатывает примерно на 65% окна.

Запас не отменяет требования к узости задачи:
одна цель, ограниченный набор файлов, один проверяемый результат.
Если ТЗ не помещается в это ограничение — это ошибка декомпозиции: эскалировать координатору, а не урезать работу молча.
