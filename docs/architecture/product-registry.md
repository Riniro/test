# Реестр продуктов и маршрутизация задач

Контур обслуживает несколько продуктов. Чтобы по задаче Jira однозначно понять, в каком репозитории
работать, продукт определяется **проектной меткой** и ищется в проверенном реестре.

Роли — [../../CLAUDE.md](../../CLAUDE.md), метки и статусы — [../ai/jira-workflow.md](../ai/jira-workflow.md),
защищённый запуск — [../ai/coordinator-runtime.md](../ai/coordinator-runtime.md).

## Главное правило безопасности

**Метка никогда не превращается напрямую в путь или команду.** Метка — только ключ поиска.
Репозиторий, базовая ветка и путь к документации берутся исключительно из записи реестра,
прошедшей валидацию. Это отсекает целый класс атак через подставленную метку Jira: текст задачи —
недоверенные данные, и подстановка его в путь или в аргумент команды недопустима.

Абсолютные пути пользователя в репозитории не хранятся: `docsPath` всегда относительный.

## Реестр

Файл `tools/registry/products.json`.

| Поле | Смысл |
| --- | --- |
| `productId` | постоянный идентификатор, не меняется при переименовании продукта |
| `name` | человекочитаемое название |
| `label` | уникальная проектная метка вида `project-test` |
| `repo` | GitHub-репозиторий в форме `owner/repo` |
| `baseBranch` | базовая ветка продукта |
| `docsPath` | относительный путь к архитектурной документации продукта |

### Регистрация продукта

1. Выбрать `productId` — короткий, постоянный, не повторяющий название. Он переживает переименования.
2. Выбрать метку вида `project-<имя>`: строчные латинские буквы, цифры и дефис, начинается с буквы или цифры.
3. Добавить запись в `products.json` **отдельным pull request**. Реестр — управляющий файл, менять его
   попутно с продуктовой задачей нельзя.
4. Прогнать `node --test`: валидация реестра покрыта тестами и поймает дубликат или опечатку.
5. Поставить новую метку на задачи продукта.

Регистрация продукта — решение человека. Автоматическое создание репозиториев в контур не входит.

### Что делает реестр непригодным

Валидация строгая и работает по принципу «всё или ничего»: при любой ошибке реестр не используется
даже частично, и ни одна запись не выбирается. Выбор «первого совпадения» запрещён — молчаливый выбор
при противоречивых данных опаснее остановки.

| Причина | Когда |
| --- | --- |
| `MISSING` | файла нет |
| `CORRUPT` | нечитаемый JSON, корень не объект, `products` не массив |
| `UNSUPPORTED_VERSION` | `version` не равен `1` |
| `INVALID_ENTRY` | запись не объект, поле отсутствует, пусто, не строка, лишнее поле, неверный формат `label`, `repo` или `docsPath` |
| `DUPLICATE_PRODUCT_ID` | повтор `productId` |
| `DUPLICATE_LABEL` | повтор `label`, без учёта регистра |

## Проектные метки

Проектной считается метка, начинающаяся с `project-`. Все прочие метки — `ai-ready`, `ai-blocked`,
`mode-mvp`, `mode-product` и любые другие служебные — в выборе продукта **не участвуют**.

Правила разрешения детерминированы и не зависят от порядка меток:

| Исход | Условие |
| --- | --- |
| `AMBIGUOUS` | уникальных проектных меток больше одной — независимо от того, зарегистрированы они или нет |
| `NEEDS_INPUT` | проектных меток нет |
| `ROUTED` | ровно одна, и она есть в реестре |
| `NEEDS_REGISTRATION` | ровно одна, и её нет в реестре |

Повтор одной и той же метки считается одной меткой. Сопоставление с реестром регистронезависимое.

Три исхода из четырёх требуют действия человека, и это намеренно: контур не угадывает продукт.

### Команда проверки маршрута

```
node tools/registry/cli.js route --labels "ai-ready,project-test,mode-mvp"
```

Печатает один объект JSON. Коды возврата: `0` — `ROUTED`, `3` — `NEEDS_INPUT`, `4` — `AMBIGUOUS`,
`5` — `NEEDS_REGISTRATION`, `6` — ошибка реестра, `2` — неверное использование.
Флаг `--registry <путь>` подменяет файл реестра; по умолчанию берётся файл рядом с `cli.js`.

Команда **только читает**: ничего не создаёт, не изменяет и не удаляет.

## Продукт и эпик — разные вещи

Это разные уровни, и путать их дорого.

**Продукт** — отдельный репозиторий со своей базовой веткой, своей документацией и своим CI. У продукта
есть запись в реестре и ровно одна проектная метка. Продукт определяет, **где** выполняется работа.

**Эпик** — группировка задач **внутри** одного продукта: крупная функциональность, этап, направление.
Эпик живёт в иерархии Jira (`Эпик` → `История`/`Задача`), не имеет записи в реестре и **не влияет на
выбор репозитория**. Эпик определяет, **что** делается.

Отсюда практические следствия:

* Новый эпик не требует новой метки `project-*` и не требует изменения реестра.
* Новый продукт требует регистрации, даже если он похож на существующий.
* Задача с меткой `project-test`, лежащая под любым эпиком, всё равно маршрутизируется в `Riniro/test`.
* Если кажется, что задаче нужны две проектные метки, — это признак, что работу надо разделить на две
  задачи, по одной на продукт. Исход `AMBIGUOUS` именно об этом и сообщает.

## Обязательная сверка Jira перед возобновлением

Маршрут, вычисленный раньше, — подсказка, а не истина. Метки задачи могли измениться между запусками:
человек мог добавить вторую проектную метку, снять метку или перевести задачу в другой статус.
Между внешним действием и записью его результата всегда есть окно, и атомарности между Jira, GitHub
и Orca не существует.

Поэтому перед возобновлением работы по задаче **обязательно**:

1. Перечитать задачу через `atlassian-v2` и сверить `key`.
2. Заново вычислить маршрут по **текущим** меткам, а не по сохранённым в журнале.
3. Если исход изменился или стал отличным от `ROUTED` — остановиться и эскалировать, а не продолжать
   по старому маршруту.
4. Сверить `runId`, `taskId` и `dispatchIds` с фактическим состоянием Orca, а `commitSha` и `prUrl` —
   с GitHub.
5. Переиспользовать существующие worker, коммит и PR, если они соответствуют задаче.

Порядок сверки для координатора в целом описан в
[../ai/coordinator-runtime.md](../ai/coordinator-runtime.md); этот раздел добавляет к нему шаг с маршрутом.

## Ограничения

* Реестр ведётся вручную; автоматического создания репозиториев нет.
* Один продукт — один репозиторий. Несколько репозиториев на продукт не поддерживаются.
* Команда маршрутизации не обращается к Jira: метки передаются ей аргументом. Их читает координатор.
* Расписания в этот этап не входят.
