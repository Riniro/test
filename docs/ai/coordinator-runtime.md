# Защищённый запуск координатора

Один координатор на репозиторий, журнал прогресса вне worktree, восстановление после аварии.
Роли — [../../CLAUDE.md](../../CLAUDE.md), SOP — [coordinator.md](coordinator.md), сбои — [recovery.md](recovery.md).

Реализация: `tools/coordinator/` — `lock.js`, `journal.js`, `cli.js`. Node.js 22, стандартная библиотека, без зависимостей.



## Зачем

Два одновременно запущенных координатора берут одну Jira-задачу, создают параллельные Run и накладывают
мутации друг друга. Прогресс при этом нигде не хранится, поэтому после аварии невозможно отличить
«действие не выполнено» от «выполнено, но не записано».

Снятая метка `ai-ready` взаимного исключения не даёт: это соглашение, а не блокировка
(см. правило 2 в [jira-workflow.md](jira-workflow.md)).

## Механизм блокировки

Блокировка — **атомарное создание каталога** через `fs.mkdirSync`. Каталог либо создаётся, либо выдаёт
`EEXIST`; третьего исхода нет. PID-файл не подходит: чтение, проверка и запись не атомарны. Удержание
эксклюзивного дескриптора тоже не подходит: Node не позволяет задать Windows share mode.

Состояние лежит вне рабочих worktree, потому что worktree удаляются после merge:

```
<stateDir>/<repoKey>/
  lock/owner.json          кто владеет блокировкой
  journal.json             прогресс
  journal.bak.json         предыдущая валидная запись
```

`stateDir` — переменная `COORDINATOR_STATE_DIR`, иначе `~/.claude-coordinator`.

`repoKey` — первые 16 hex SHA-256 от нормализованного пути `git rev-parse --git-common-dir`. Этот путь
одинаков для **всех** worktree одного репозитория, поэтому они делят одну блокировку, а разные
репозитории не мешают друг другу.

Владение подтверждается token из `owner.json`. Снять блокировку может только владелец.
**Истечение TTL само по себе захват не разрешает:** просроченная блокировка лишь помечается `stale: true`,
а `acquire` по-прежнему возвращает `BUSY`. Снять её можно только явным решением человека.

`owner.json` содержит ровно семь полей: `token`, `pid`, `host`, `repoKey`, `worktree`, `acquiredAt`,
`heartbeatAt`. Посторонние данные вызывающего туда не попадают.

## Журнал прогресса

`journal.json` хранит `issueKey`, `stage`, `runId`, `taskId`, `dispatchIds`, `branch`, `commitSha`,
`prUrl`, `lastConfirmedAction` (`{ name, at, result }`), `updatedAt` и `checksum`.

Запись атомарна: временный файл рядом, `fsync`, затем `rename`. Прерывание процесса никогда не подменяет
`journal.json` частично записанным файлом. Повреждение обнаруживается по двум признакам: нечитаемый JSON
даёт `CORRUPT`, несовпадение контрольной суммы — `CHECKSUM_MISMATCH`. Контрольная сумма сверяется всегда,
в том числе когда поле `checksum` равно `null`. Предыдущая валидная запись сохраняется в `journal.bak.json`
и повреждённой записью не затирается.

**Секреты в журнал не пишутся:** ни значений окружения, ни токенов, ни ключей.

## Команды

| Команда | Назначение | Коды возврата |
|---|---|---|
| `start -- <команда> <аргументы>` | Захватить блокировку и запустить дочерний процесс | код дочернего процесса; `9` если занято |
| `status` | Состояние блокировки и журнала | `0` свободна, `9` занята, `10` журнал повреждён |
| `release --token <token>` | Освобождение владельцем | `0`; `11` при `NOT_OWNER` |
| `force-release --confirm --reason "<текст>"` | Явный ручной перехват | `0`; `12` без обоих флагов |
| `recover` | Диагностика и вердикт | `0` при `SAFE_TO_RELEASE`, `13` при `UNCERTAIN` |

Штатная остановка — завершение дочернего процесса (`Ctrl+C` либо `SIGTERM`): обработчики сигналов
освобождают блокировку сами.

`recover` выдаёт `SAFE_TO_RELEASE` только когда блокировка существует, владелец известен, его процесс мёртв
и в журнале нет незавершённого внешнего действия. Во всех остальных случаях — `UNCERTAIN` с перечислением
причин. **`recover` никогда не снимает блокировку сам.**

Все автоматические запуски координатора идут только через `start`. Глобальный launcher обычных
интерактивных сессий Claude не меняется: обычная сессия не владеет Jira-задачей.

## Возобновление: сверка перед действием

Журнал — подсказка, а не истина. Между внешним действием и записью его результата всегда есть окно,
и **атомарности между Jira, GitHub и Orca не существует**. Порядок при возобновлении:

1. Прочитать журнал. При `CORRUPT` или `CHECKSUM_MISMATCH` — остановиться и эскалировать, не угадывая стадию.
2. Сверить `issueKey` с фактическим состоянием Jira: статус, метки, последний комментарий-журнал.
3. Сверить `runId`, `taskId` и `dispatchIds` с `orca orchestration worker-list --run <runId>`.
4. Сверить `commitSha` и `prUrl` с фактическим состоянием GitHub.
5. **Переиспользовать** существующие worker, коммит и PR, если они соответствуют задаче, а не создавать новые.
6. Если `lastConfirmedAction.result` равен `pending` — внешнее действие могло выполниться, но не записаться.
   Сначала сверка, только потом решение. Повторять внешнее действие вслепую запрещено.

## Ограничения

* Блокировка действует в пределах **одного хоста**. Общей блокировки между машинами нет.
* `recover` не проверяет Jira — только Orca и GitHub. Jira сверяет Claude вручную по шагу 2 выше.
* Просроченная блокировка не снимается автоматически никогда.
* Расписания и автозапуск в этот этап не входят.
* `processAlive` определяется по PID, а PID может быть переиспользован ОС. Поэтому «процесс жив» —
  признак, а не доказательство, и вердикт по умолчанию — `UNCERTAIN`.

## Проверено на практике

Помимо автоматических тестов (`node --test` — 121 зелёный) команда проверена запуском на Windows.
Воспроизведение велось отдельным временным JS-файлом и `process.execPath` с аргументами массивом,
без `node -e` и без shell-экранирования, с фиксацией stdout, stderr и кода завершения.

| Сценарий | Результат |
| --- | --- |
| Команда запускается, аргумент доходит до дочернего процесса, stdout и stderr проходят наружу | подтверждено |
| Код возврата дочернего процесса пробрасывается (`42`) | подтверждено |
| Пока дочерняя команда работает, второй запуск получает `9` и `BUSY`, свою команду не запускает | подтверждено |
| После штатного завершения каталог блокировки удалён | подтверждено |
| Несуществующая дочерняя команда даёт ненулевой код и освобождает блокировку | подтверждено |
| Авария оболочки (`SIGKILL` процессу CLI) при живом дочернем процессе оставляет блокировку захваченной, второй координатор получает `BUSY` | подтверждено |

Последний сценарий — ключевой: истечение времени само по себе захват не разрешает, поэтому упавший
координатор не освобождает место автоматически. Снятие такой блокировки — явное решение человека
через `force-release`.
