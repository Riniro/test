# Контракт ТЗ для Qwen-воркера

Формальный шаблон задания. Заполняет Claude, исполняет Qwen по правилам [../../QWEN.md](../../QWEN.md).

## Инварианты
- **Ровно один проверяемый результат** на задачу. Два результата — две задачи.
- **ТЗ называет тип задания** — `change` или `investigation` ([../../QWEN.md](../../QWEN.md)).
  Типы не смешиваются: разбор и правка — всегда два разных задания.
- ТЗ самодостаточно: воркер не читает Jira и не имеет доступа к брифу.
- ТЗ вместе с затрагиваемыми файлами должно помещаться в контекст **250000 токенов**: столько сообщает
  сервер модели, на это же значение настроен клиент, авто-сжатие срабатывает примерно на 65% окна
  ([../../QWEN.md](../../QWEN.md)).
- **Запас окна не отменяет узкой декомпозиции.** Одна цель, ограниченный набор файлов, один
  проверяемый результат — требование прежнее. Каждое задание исполняется отдельным dispatch в свежей
  сессии воркера; несколько заданий подряд в одном терминале не ведутся. ТЗ, не помещающееся в окно, —
  ошибка декомпозиции: дробить до начала работы, а не урезать объём работы молча.
- Все пути внутри репозитория — относительные от его корня. Абсолютные пути пользователя запрещены;
  единственное исключение — путь отчёта `investigation`, который обязан быть вне репозитория.

## Шаблон задания `change`
```markdown
# Задача <taskId> — тип: change

## Цель
Одно предложение: что должно начать работать после этой задачи.

## Контекст
2–5 строк: текущее поведение и почему оно меняется.
Ссылки на файлы репозитория, без пересказа их содержимого.

## Точный scope
- <конкретное изменение 1>
- <конкретное изменение 2>

## Запрещённый scope
- Изменение любых файлов вне списка ниже.
- Рефакторинг, переформатирование, переименования.
- Добавление зависимостей, изменение package.json.
- Изменение публичного API (если не указано в «Точный scope»).
- Работа с Jira, PR, ветками, merge.

## Ожидаемые файлы
- src/<file>.js        (изменение)
- test/<file>.test.js  (изменение/создание)

## Acceptance criteria
1. <проверяемое утверждение>
2. <проверяемое утверждение>
Каждый пункт покрыт тестом.

## Test commands
- node --test
- git diff --check

## Commit message
<одна строка в императиве, <= 72 символов>

## Как воркер сообщает о завершении
Отдельной команды `orca orchestration worker_done` не существует. Завершение — подтип сообщения:

    orca orchestration send --from <handle> --type worker_done \
      --subject "<короткий статус>" --body "<сводка из трёх предложений>" \
      --task-id <taskId> --dispatch-id <dispatchId> --outcome succeeded

Handle и оба идентификатора берутся **из преамбулы dispatch**, а не из ТЗ: координатор пишет ТЗ до создания dispatch, и этих значений в нём нет. Готовая строка лежит в блоке `=== CLI COMMANDS ===` преамбулы.

`--outcome` обязателен. Отправляется ровно один раз и только при зелёных acceptance-командах.

**В ТЗ идентификаторы не подставлять.** В разделе «Завершение» ТЗ даётся ссылка на преамбулу. Закреплять в ТЗ или в общих документах идентификаторы конкретного dispatch запрещено: каждый воркер действует полномочиями своего dispatch, а чужие ID не засчитываются.

Правила сохранения команды на случай сжатия контекста — в [../../QWEN.md](../../QWEN.md).
```

## Шаблон задания `investigation`
```markdown
# Задача <taskId> — тип: investigation

## Цель
Одно предложение: на какой вопрос должен ответить отчёт.

## Источники данных
- <путь к логу, команда, диапазон, идентификаторы run/dispatch>

Только перечисленные источники. Недоступные данные описываются как недоступные; догадка вместо
данных запрещена.

## Что нужно установить
1. <проверяемый вопрос>
2. <проверяемый вопрос>

## Запрещённый scope
- Любые изменения репозитория: коммиты, новые и изменённые файлы, черновики.
- Исправление найденного — это отдельное задание типа `change`.
- Работа с Jira, PR, ветками, merge.

## Отчёт
Путь: `%TEMP%\<имя>.md` — вне репозитория, другого места нет.
Структура, все четыре раздела обязательны:
1. **Вывод** — не более пяти строк, ответ на вопрос из «Цели».
2. **Факты** — у каждого пункта ссылка на свидетельство: `файл:строка`, команда с выводом или идентификатор.
3. **Предположения** — выведенное и непроверенное, с указанием, чего не хватило для проверки.
4. **Приложение** — полные данные, таблицы, выдержки.

## Acceptance criteria
1. Отчёт существует по указанному пути и содержит все четыре раздела.
2. Каждый пункт раздела «Факты» имеет проверяемую ссылку.
3. Репозиторий не изменён: `git status --short` пуст, `HEAD` не сдвинут.

## Test commands
- git status --short
- git rev-parse HEAD

## Завершение
Штатный `worker_done` с идентификаторами своего dispatch (см. преамбулу).
`--body` — не более трёх предложений: главный вывод и путь к отчёту. Полные данные в сообщение
не копируются.
```

## Независимая приёмка отчёта `investigation`

Отчёт принимается только при выполнении **всех пяти** условий. Любое невыполненное — возврат воркеру
или эскалация, по [recovery.md](recovery.md).

1. `settle.js watch` вернул `SETTLED_BY_WORKER` (код `0`) с совпадающими Task и Dispatch ID.
2. Репозиторий не тронут: `git -C <worktree> status --short` пуст **и** `git -C <worktree> rev-parse HEAD`
   равен базовому коммиту, зафиксированному при создании worktree.
3. Файл отчёта существует ровно по пути из ТЗ и непуст.
4. В отчёте присутствуют все четыре раздела, и у каждого пункта «Фактов» есть ссылка на свидетельство.
   Координатор **самостоятельно перепроверяет не менее двух** фактов — тех, на которых держится главный
   вывод.
5. Сводка в `worker_done` не противоречит отчёту.

Выводы отчёта решением не являются: решение принимает координатор.

### Если `worker_done` не пришёл

Для `investigation` вердикт `WORK_PRESENT_UNSETTLED` (код `20`) **не означает выполненную работу**.
`settle.js` берёт последний коммит worktree и не отличает базовый коммит от коммита воркера, а флаг
`--worktree` обязателен, поэтому у investigation-задания «коммит есть» всегда. Признак выполнения
здесь другой: отчёт по пути из ТЗ плюс совпадение `HEAD` с базовым коммитом. Трактовать код `20`
как успех запрещено.

## Ветка и worktree
Каждая задача исполняется в отдельном new-child worktree; ветка указывается в ТЗ явно.
Воркер не переключает и не создаёт ветки сам. Для `investigation` worktree нужен всё равно: он задаёт
рабочий каталог и базовый коммит, с которым сверяется неизменность репозитория.

## Блокировка
Противоречие или нехватка данных → `orca orchestration ask`, без `worker_done`.
Красные тесты → escalation, разбор по [recovery.md](recovery.md).
