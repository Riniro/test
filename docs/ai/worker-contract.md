# Контракт ТЗ для Qwen-воркера

Формальный шаблон задания. Заполняет Claude, исполняет Qwen по правилам [../../QWEN.md](../../QWEN.md).

## Инварианты
- **Ровно один проверяемый результат** на задачу. Два результата — две задачи.
- ТЗ самодостаточно: воркер не читает Jira и не имеет доступа к брифу.
- ТЗ должно помещаться в контекст 55000 токенов вместе с затрагиваемыми файлами.
- Все пути — относительные от корня репозитория. Абсолютные пути пользователя запрещены.

## Шаблон
```markdown
# Задача <taskId>

## Цель
Одно предложение: что должно начать работать после этой задачи.

## Контекст
2–5 строк: текущее поведение и почему оно меняется.
Ссылки на файлы репозитория, без пересказа их содержимого.

## Точный scope
- <конкретное изменение 1>
- <конкретное изменение 2>

## Запрещённый scope
- Изменение любых файлов вне списка ниже.
- Рефакторинг, переформатирование, переименования.
- Добавление зависимостей, изменение package.json.
- Изменение публичного API (если не указано в «Точный scope»).
- Работа с Jira, PR, ветками, merge.

## Ожидаемые файлы
- src/<file>.js        (изменение)
- test/<file>.test.js  (изменение/создание)

## Acceptance criteria
1. <проверяемое утверждение>
2. <проверяемое утверждение>
Каждый пункт покрыт тестом.

## Test commands
- node --test
- git diff --check

## Commit message
<одна строка в императиве, <= 72 символов>

## worker_done format
{
  "taskId": "<taskId>",
  "dispatchId": "<dispatchId>",
  "status": "done",
  "branch": "<branch>",
  "commit": "<sha>",
  "files": ["<изменённые файлы>"],
  "tests": "node --test — PASS, <N> passed / 0 failed"
}
Отправляется ровно один раз и только при зелёных acceptance-командах.
```

## Ветка и worktree
Каждая задача исполняется в отдельном new-child worktree; ветка указывается в ТЗ явно.
Воркер не переключает и не создаёт ветки сам.

## Блокировка
Противоречие или нехватка данных → `orca orchestration ask`, без `worker_done`.
Красные тесты → escalation, разбор по [recovery.md](recovery.md).
