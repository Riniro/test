# Восстановление после сбоев

Применяется координатором (Claude). Общий принцип: **сначала диагностика, потом ровно одно действие**.
Дублирование prompt'ов и параллельные воркеры на одну задачу запрещены — они порождают двойные коммиты.

## 1. Известный случай: Qwen `agent_prompt_stalled`
Симптом: dispatch отправлен, воркер не начал работу, статус завис.

Порядок:
1. **Не дублировать prompt.** Повторная отправка того же задания запрещена.
2. **Не создавать второго воркера** на ту же задачу.
3. Диагностика — три источника, все три:
   - `worker-show` — жив ли воркер, какова его capability;
   - `worker-read` — что реально видно в терминале воркера;
   - `dispatch-show` — состояние dispatch и его `dispatchId`.
4. Если полный prompt **находится в composer** и capability **действительна** — отправить
   **ровно один bare Enter**: `orca terminal send --terminal <handle> --enter` без `--text`
   (флаги `--wait-submit` и `--retry-request` требуют `--text` и с голым Enter несовместимы).
   Признак действительной capability — `capability_revoked_at: null` **и** `status: dispatched`
   в выводе `dispatch-show`. Поле `capability_hash` для этого непригодно: в связке с `qwen-code`
   оно равно `null` и у успешно завершившихся dispatch.
   Пустой composer — это **не** данный случай, см. §5.
5. Проверить через `worker-read`, что воркер начал работу (появился вывод агента, а не эхо prompt'а).
6. Если не начал — **одна повторная попытка** шагов 3–5.
7. После неудачи второй попытки: задача → `ai-blocked` + Flagged = `Impediment`, комментарий с
   Run ID, Task ID, Dispatch ID и наблюдаемым состоянием, эскалация человеку. Run завершается.

## 2. Crash координатора или воркера
1. Не начинать заново вслепую. Сначала восстановить состояние:
   `git log --oneline` в worktree воркера, `git status --short`, `dispatch-show` по всем известным dispatchId.
2. Если commit воркера уже существует — считать задачу выполненной и идти в ревью
   ([review-checklist.md](review-checklist.md)), а не перезапускать работу.
3. Если commit'а нет, а дерево грязное — **ничего не удалять и не сбрасывать**: зафиксировать состояние
   в Jira-комментарии и эскалировать. `reset --hard`, `clean -fd`, `git stash` запрещены.
4. Освободить зависшие worker terminals, убедиться в отсутствии `pending`/`unknown` dispatch.

## 3. Stale Jira claim
Признак: задача не в `To Do`, метки `ai-ready` нет, но активного run'а по ней нет
(нет свежих комментариев с Run ID, все dispatch завершены или отсутствуют).

1. Перечитать задачу, сверить `key`, прочитать последний комментарий-журнал.
2. Определить фактическую стадию по журналу: бриф собран? коммиты есть? PR создан?
3. Продолжить с этой стадии в рамках **нового** Run ID, добавив комментарий о перехвате.
4. Если стадию определить невозможно — `ai-blocked` + Flagged = `Impediment` и эскалация.
   Заново «с нуля» задача не перезапускается: риск потерять уже сделанные коммиты.

## 4. Failed tests
1. Зелёный результат подтверждает только собственный запуск Claude (`node --test`), не отчёт воркера.
2. Красные тесты у воркера → `worker_done` не отправляется; воркер эскалирует.
3. Claude определяет причину: ошибка реализации или ошибка acceptance criteria в ТЗ.
   - Ошибка реализации → `CHANGES_REQUIRED` с нумерованным списком правок, метка `ai-changes-requested`.
   - Ошибка ТЗ → ТЗ переписывается координатором; это **не** расходует итерацию воркера.
4. Максимум две итерации исправлений, затем `ai-blocked` + Flagged=Impediment и эскалация.
5. Коммит с красными тестами не интегрируется и не попадает в PR
   (см. [../architecture/quality-gates.md](../architecture/quality-gates.md)).

## 5. Prompt не доставлен в только что созданный worktree
Симптом похож на §1, но composer **пуст**: `worker-start` вернул `state: ready` и `stage: input_accepted`,
воркер `live`, `nextAction: none`, а работы нет.

1. Подтвердить, что работа не начиналась, тремя фактами сразу: пустой composer в `worker-read`,
   нетронутое дерево worktree (`git status --short` пуст, коммитов нет) и пустой лог сессии агента.
2. Bare Enter **не отправлять**: отправлять нечего, условие §1.4 не выполнено.
3. Это положительное доказательство, что dispatch не начинался, поэтому дублирования работы быть не может:
   выполнить `worker-stop`, затем **ровно один** `worker-start --retry-of <dispatchId>` с той же Task
   и тем же worktree. `--retry-of` не наследует placement — повторить `--worktree` и `--agent` явно.
   `--retry-of` несовместим с `--spec`: он требует `--task` с исходной Task.
4. Новые Run и Task для обхода не создавать.
5. Профилактика: создавать worktree отдельной командой заранее и запускать воркера в готовый.

## 6. Воркер упёрся в лимит контекста
Признаки: в терминале сообщение о сжатии контекста, после которого воркер уверенно сообщает, что всё
сделано и `worker_done` отправлен, хотя коммита нет и дерево грязное. Отчёту воркера не верить никогда:
проверять `git log` и `git status` самому.

1. Зафиксировать состояние: `git log --oneline`, `git status --short`, результат `node --test`,
   Task и Dispatch ID.
2. `worker-stop`; при ответе `stop_unknown` — `worker-show` для инспекции, затем `worker-abandon`
   и закрытие терминала. `reset`, `clean` и `stash` запрещены, worktree сохраняется.
3. Запустить свежего воркера **в новом терминале** — переиспользование исчерпанного терминала
   бесполезно, его контекст уже заполнен.
4. Вывод на будущее: лимит контекста воркера — **250000 токенов**, авто-сжатие срабатывает примерно
   на 65% окна ([../../QWEN.md](../../QWEN.md)). Запас окна узкой декомпозиции не отменяет: задача,
   где файл с реализацией и его тесты вместе подходят к этому объёму, декомпозирована неверно —
   дробить до начала работы, а не рассчитывать на сжатие.
