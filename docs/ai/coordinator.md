# SOP координатора (Claude)

Исполнимая последовательность одного coordinator-run. Шаги выполняются по порядку, без пропусков.
Роли — [../../CLAUDE.md](../../CLAUDE.md), Jira — [jira-workflow.md](jira-workflow.md).

## 0. Подготовка
Координатор запускается через защищённую команду, удерживающую блокировку репозитория, чтобы на одном
хосте не работали два координатора сразу — см. [coordinator-runtime.md](coordinator-runtime.md).

### 0.1 Preflight worktree координатора
Выполняется **первым делом**: до чтения остального SOP, до Jira и до Orca. Цель — убедиться, что run
начинается в своём worktree, на своей ветке и на актуальном `origin/master`.

Устаревший worktree координатора означает устаревшие `CLAUDE.md`, `QWEN.md` и сам SOP: все решения run
принимаются по неверным правилам, а воркер получает устаревший контракт. Именно так в KAN-9 воркеру
ушёл `QWEN.md` из состояния, отстававшего от `master` на 31 коммит.

| Что проверяется | Команда | Требование |
|---|---|---|
| Путь | `git rev-parse --show-toplevel` | worktree координатора, не master-дерево и не worktree воркера |
| Ветка | `git branch --show-current` | ветка координатора |
| HEAD | `git rev-parse --short HEAD` | зафиксировать в журнале run |
| Чистота | `git status --short` | пусто |
| Расхождение | `git fetch origin --prune`, затем `git rev-list --left-right --count HEAD...origin/master` | 0 собственных коммитов впереди |

Единственное разрешённое действие при отставании от `origin/master` — `git merge --ff-only origin/master`.
Если fast-forward не проходит, он не форсируется.

Run **не начинается**, выполняется остановка с сообщением человеку, если:
* дерево грязное — незакоммиченные изменения сохраняются как есть, они могут быть чужими;
* впереди `origin/master` есть собственные коммиты — состояние разбирает человек;
* путь или ветка не соответствуют worktree координатора.

Запрещены при любом исходе preflight: `git reset --hard`, `git checkout -- <путь>`, `git restore`,
`git clean`, `git stash`, `push --force`. Чужие изменения не отбрасываются никогда —
см. [../../AGENTS.md](../../AGENTS.md).

### 0.2 Форма команд в чужом рабочем дереве
Любая команда, относящаяся не к текущему каталогу, называет рабочее дерево **явно**:
`git -C <путь> status --short`, `git -C <путь> rev-parse HEAD`, `git -C <путь> log --oneline -1`.

Смена каталога перед командой — `cd <путь> && git …` — не применяется. Причина не в стиле: составная
команда скрывает, к какому дереву относится результат, и переносит состояние между шагами run.
То же правило действует для `gh` и `node`: каталог задаётся флагом команды, а не переходом.

### 0.3 Остальная подготовка
1. `orca skills get orchestration --full` — загрузить актуальный orchestration guide.
   Guide из памяти считается устаревшим.
2. Preflight по 0.1 пройден: путь, ветка, HEAD, чистое дерево, отсутствие расхождения зафиксированы.
3. Зафиксировать **Run ID** для журнала в Jira.

## 1. Найти задачу
4. Через `atlassian-v2` найти задачи проекта KAN с меткой `ai-ready`.
5. Выбрать **одну** (самую приоритетную/старшую). Больше одной задачи за run не берётся.

## 2. Забрать в работу (claim)
6. Перечитать задачу по `key`, сверить ключ и наличие `ai-ready`.
7. Claim выполняется **двумя последовательными шагами с проверкой каждого**
   (правило 2 в [jira-workflow.md](jira-workflow.md)): `editJiraIssue` снимает `ai-ready`, сохраняя
   чужие метки, затем `transitionJiraIssue` переводит в Brief (`10007`, transition `41`).
   Атомарности между шагами нет, и Jira её не предоставляет.
   Если `ai-ready` уже снята кем-то — задача занята, run завершается.

## 3. Бриф
8. Собрать бриф по [brief-template.md](brief-template.md), максимум пять сгруппированных вопросов за раунд.
9. **Остановиться при недостатке данных:** метка `ai-needs-input`, комментарий с вопросами, run завершён.
10. Определить режим: `mode-mvp` или `mode-product`. Опубликовать бриф комментарием.

## 4. Декомпозиция
11. Построить DAG задач: узел = одна задача с **одним** проверяемым результатом
    (формат ТЗ — [worker-contract.md](worker-contract.md)), рёбра = зависимости по файлам и API.
12. Узлы, делящие один файл, обязаны быть последовательными, а не параллельными.

## 5. Запуск воркеров
13. Перевести задачу в In Progress (`10005`, transition `21`).
14. Для каждого готового узла DAG создать **new-child worktree** и запустить Qwen-воркера.
15. Одновременно выполняются **максимум два независимых** воркера.
16. Для `qwen-code` **не передавать `--model`** — Qwen резолвит собственную настройку `llm_model`.
17. Записать `taskId` и `dispatchId` каждого dispatch в журнал.
18. Пока воркер активен, координатор **не вносит собственных правок в его worktree**: свои изменения
    он готовит в worktree координатора, а интеграция идёт коммитами — до запуска воркера либо после
    settlement. Незакоммиченные правки другого автора в рабочем дереве воркера запрещены.

## 6. Ожидание
19. Ожидание результата воркера — **один блокирующий вызов с конечным дедлайном**:

        node tools/coordinator/settle.js watch --run <runId> --task <taskId>           --dispatch <dispatchId> --worktree <путь> --deadline-ms <N> > <лог вне репозитория> 2>&1

    stdout — один JSON с вердиктом, полный вывод уходит в файл вне репозитория. Опрос выполняет сам
    скрипт внутри вызова. Периодические проверки моделью, циклы `while true` и повторные ручные
    `worker-list` для «посмотреть, как там» запрещены: они ничего не добавляют к свидетельствам.
20. `deadlineExceeded: true` означает **незавершённое ожидание**, а не доказанный провал работы.
    Ни успех, ни неудача из истёкшего дедлайна не выводятся — разбор по
    [recovery.md](recovery.md), §7.
21. `question` → ответить по брифу; если ответа нет в брифе — `ai-needs-input` и остановка.
22. Зависание или сбой → [recovery.md](recovery.md). Дубль prompt'а и второй воркер на ту же задачу запрещены.

## 7. Независимая проверка
23. Для каждого commit **независимо**: `git show --stat <sha>`, чтение diff.
24. Запустить `node --test` и `git diff --check` самому (отчёту воркера не доверять).
25. Ревью по [review-checklist.md](review-checklist.md) → вердикт `ACCEPT` или `CHANGES_REQUIRED`.
26. `CHANGES_REQUIRED` → метка `ai-changes-requested`, вернуть воркеру нумерованный список правок.
    Максимум две итерации, затем `ai-blocked` + Flagged=Impediment и эскалация.

## 8. Интеграция
27. Интегрировать **только ACCEPT-коммиты**. Непринятые остаются в своих worktree.
28. Прогнать `node --test` на интеграционной ветке целиком.
29. Создать PR. **Merge не выполнять** — merge делает человек.
30. Ожидание CI — **один блокирующий вызов с явным конечным дедлайном**. Своего таймаута у
    `gh run watch` нет, поэтому дедлайн задаётся внешней командой `timeout`:

        timeout <сек> gh run watch <runId> --exit-status --interval 20 > <лог вне репозитория> 2>&1

    | Код возврата | Значение |
    |---|---|
    | `0` | прогон завершён успешно |
    | `124` | дедлайн истёк — **ожидание не завершено**, это не провал |
    | иной ненулевой | прогон завершился неуспешно либо ошибка `gh` |

    При `124` в журнал записываются ID прогона и состояние «ожидание не завершено»; дальше по
    [recovery.md](recovery.md), §7. Таймаут инструмента, переводящий команду в фон, ожидание
    **не прекращает** и конечным дедлайном не является.
31. **Финальная сверка обязательна** и к «лишним вызовам» не относится: зелёными считаются только те
    job'ы, чей `head_sha` совпадает с актуальным head PR.

        gh api repos/<owner>/<repo>/pulls/<N> --jq .head.sha
        gh api repos/<owner>/<repo>/actions/runs/<runId>/jobs --jq '.jobs[] | {name, conclusion, head_sha}'

32. Смена head во время ожидания: результаты прежнего прогона недействительны. Ожидание и сверка
    повторяются на новом коммите. Переносить вердикт со старого SHA на новый запрещено.

## 9. Завершение
33. Обновить Jira: In Review (`10006`, transition `31`), метка `ai-awaiting-merge`, комментарий с
    Run ID, Task ID, Dispatch IDs, ветками, коммитами, результатами тестов, вердиктом и PR URL.
    Done (`10008`) — только после подтверждённого merge, то есть в отдельном последующем run.
34. **Освободить worker terminals** после settlement каждого dispatch.
35. Проверить, что не осталось dispatch в состоянии `pending` или `unknown`.
    Любой неразрешённый dispatch — не завершать run: либо довести до settlement, либо `ai-blocked` и эскалация.

## 10. Автономный режим

Автономный режим ведёт **Qwen-координатор** по собственному контракту
([qwen-coordinator.md](qwen-coordinator.md)); Claude в нём отвечает за архитектурные решения,
независимое ревью и сложные исключения. Роли не смешиваются: запреты implementation-воркера
([../../QWEN.md](../../QWEN.md)) остаются в силе целиком.

### Очередь
Проверяется без участия Claude:

    node tools/jira/queue.js --project KAN --labels project-test,ai-ready

Коды: `0` — очередь непуста, `3` — пуста, `4` — источник недоступен или аутентификация не прошла,
`2` — неверное использование. **Код `4` не равен коду `3`**: недоступность Jira никогда не считается
отсутствием задач и прогон при ней не начинается.

Фильтр конъюнктивный: нужны все метки сразу. На первом этапе берутся только задачи с `project-test`
и `ai-ready`. Одновременно ведётся **одна** задача на репозиторий.

Учётные данные Jira лежат в файле **вне репозитория** и в вывод не попадают — см.
[../../AGENTS.md](../../AGENTS.md).

### Два канала ожидания
Результат ждёт `settle.js watch`, вопросы — `orca orchestration check --wait --types "question,escalation"`.
Это разные каналы, и слушать нужно оба.

**У одного run может быть только один активный ожидатель.** Второй параллельный `check --wait`
немедленно отклоняется с `waiter_exists` и ничего не слушает — проверено на практике. Поэтому
ожидатель держится один и **перезапускается** после обработки каждой партии сообщений.

### Обращение к человеку
Только через Jira: комментарий и метка `ai-needs-input`. Поводов ровно три — продуктовое решение,
недостающая авторизация, действие, которое может выполнить только человек (merge, подтверждение в UI,
выдача токена). Технические развилки решают координатор и Claude.

Интерактивные инструменты агента каналом связи с человеком не являются: в этом репозитории
`ask_user_question` отключён файлом `.qwen/settings.json`. Этот файл хранится в том виде, в который
его приводит миграция самого агента, иначе каждый запуск воркера оставляет незакоммиченную правку.

### Автозапуск
Запуск по расписанию с условной проверкой очереди — `orca automations create` с `--trigger` и
`--precheck`: код `0` от precheck продолжает прогон, любой другой записывает пропуск. Благодаря этому
пустая очередь не расходует ни Claude, ни Qwen.

Автозапуск включается **только из принятой версии после merge** и требует работающего runtime Orca:
на Windows `orca serve --supervise` недоступен, поэтому перезагрузку хоста автоматический режим
сам не переживает.
