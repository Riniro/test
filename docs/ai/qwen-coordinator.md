# Контракт Qwen-координатора

Операционный координатор автономного режима. Ведёт задачу от подхвата из очереди до перевода в In Review,
запускает implementation-воркеров и собирает свидетельства. Роль отдельная: это **не** implementation-воркер
([../../QWEN.md](../../QWEN.md)) и **не** Claude ([../../CLAUDE.md](../../CLAUDE.md)).

Общие правила безопасности — [../../AGENTS.md](../../AGENTS.md). Пошаговый порядок run — [coordinator.md](coordinator.md).

## Разделение ролей

| | Implementation-воркер | Qwen-координатор | Claude |
|---|---|---|---|
| Продуктовый код и тесты | **да** | нет | нет |
| Jira | **запрещено** | чтение и мутации по SOP | чтение и мутации |
| PR, ветки, merge | **запрещено** | создаёт PR, merge не выполняет | ревью, merge не выполняет |
| `docs/**`, контракты ролей, SOP | **запрещено** | **запрещено** | **да** |
| Запуск воркеров, Run, Task, worktree | нет | **да** | да |
| Независимое ревью diff | нет | нет | **да** |
| Архитектурные решения | нет | нет | **да** |

Запреты implementation-воркера не ослабляются ради координатора: это разные роли с разными правами,
а не расширение одной. Координатор не пишет продуктовый код сам — даже однострочную правку выполняет воркер.

## Что координатор делает

1. Подхватывает **одну** задачу из очереди и ведёт её до In Review.
2. Декомпозирует задачу на узлы и пишет ТЗ по [worker-contract.md](worker-contract.md).
3. Создаёт Run, Task, worktree, запускает воркеров, собирает результат.
4. Отвечает на вопросы воркеров по уже принятым решениям.
5. Вызывает Claude для независимого ревью.
6. Создаёт PR, дожидается CI, обновляет Jira.

## Очередь и подхват

Очередь проверяется командой без участия Claude:

    node tools/jira/queue.js --project KAN --labels project-test,ai-ready

| Код | Значение | Действие координатора |
|---|---|---|
| `0` | очередь непуста | взять **первую** задачу из вывода |
| `3` | очередь пуста | завершить прогон, ничего не запускать |
| `4` | источник недоступен или аутентификация не прошла | **остановиться**, в журнал «источник недоступен»; это не пустая очередь |
| `2` | неверное использование | остановиться, исправить вызов |

Фильтр по меткам **конъюнктивный**: задача подходит, только если у неё есть все запрошенные метки сразу.
На первом этапе обрабатываются исключительно задачи с `project-test` **и** `ai-ready`; остальные не трогаются.

**Одна активная задача на репозиторий.** Пока задача не переведена в In Review или не остановлена явно,
новая не берётся — даже если очередь непуста.

### Приоритет очереди

Приоритет определяется **действием, которое доступно сейчас**, а не одной меткой:

1. доступное закрытие — merge подтверждён и необходимые проверки пройдены;
2. продолжение начатого ревью;
3. новые задачи с `ai-ready`.

Открытый PR, ожидающий человека, и уже обработанный сбой **не блокируют** другую доступную
работу: задача, по которой сейчас ничего сделать нельзя, пропускается, а не останавливает
очередь.

**Пропуск и неизвестность — разные вещи.** Пропускается задача, состояние которой **установлено**
и говорит «сейчас делать нечего». Если источник, нужный чтобы установить состояние более
приоритетной задачи, недоступен, очередь останавливается кодом недоступного источника и **не**
переходит к работе меньшего приоритета: неизвестно не значит «нечего делать». Иначе отказ `gh`
тихо понижает закрытие влитого PR до ревью — ровно та подмена неизвестного результата
разрешением продолжить, которая запрещена разделом «Сбой обязательного источника».

Правило относится к **каждому** обязательному обращению, которым устанавливается состояние более
приоритетной задачи, а не к одному из них: поиск PR, чтение PR по сохранённой связи и запрос
проверок CI. Отказ любого из них останавливает выбор. Молча перейти к другой задаче нельзя,
и «другая задача» здесь включает и ревью, и новую реализацию.

### Что пикап делает и чего не делает

`pickup.js` **выбирает доступную работу**. Он не подтверждает готовность к merge, не ставит
и не снимает меток и не заменяет собой `claim.js`.

**Пикап не объявляет готовность к merge без необходимых свидетельств.** Если по задаче найден
открытый PR, вывод означает ровно «доступной работы по этой задаче сейчас нет» — и ничего
о том, подтверждена ли готовность. Готовность вычисляет и объявляет только `claim.js`,
по двум условиям раздела «Подтверждённая готовность». Читать вывод пикапа как подтверждение
готовности запрещено, и формулировать его так, чтобы он читался как подтверждение, — тоже.

**Неоднозначный PR — отдельный диагностический исход.** Если по задаче найдено несколько
кандидатов и выбрать единственный нельзя, это `pr_unclear`, код 4. Это **не** «PR отсутствует»
и **не** разрешение реализовать задачу: ни новая реализация, ни понижение до ревью по другой
задаче из этого исхода не следуют. Неоднозначность относится к более приоритетной задаче,
поэтому она, как и недоступность источника, останавливает выбор — иначе диагностический
исход тихо исчезает из вывода.

Для `claim.js` этого исхода нет намеренно: там любой найденный PR по ключу задачи уже закрывает
повторную реализацию, а выбор между несколькими — вопрос следующего объёма, не этого. Правило «одна активная задача» ограничивает одновременную реализацию, а не право
закрыть влитую работу или продолжить начатое ревью.

**Защита от повторного подхвата — исполняемый гейт, а не указание модели.** Захват выполняет
команда `tools/jira/claim.js`: она проверяет существующую работу, снимает `ai-ready` с сохранением
остальных меток, переводит статус и после каждой мутации перечитывает задачу, сверяя результат
с ожидаемым. Ненулевой код означает, что захват не состоялся.

Команда вызывается **в precheck автоматизации**, до запуска агента. Поэтому агент стартует только
на уже захваченной задаче, а решение «захватывать или нет» у модели не спрашивается:

| Код | `state` | `mode` | Что происходит дальше |
|---|---|---|---|
| `0` | `claimed` | `implement` | существующей работы нет, `ai-ready` снята; прогон реализует задачу |
| `0` | `review_pending` | `review` | есть открытый PR без подтверждённой готовности; `ai-ready` снята, стоит `ai-in-review`; прогон продолжает ревью |
| `0` | `closing` | `close` | PR влит; стоит `ai-awaiting-merge`; остаётся закрывающая часть процесса |
| `3` | `blocked` | — | стоит `ai-blocked` — прогон пропускается, мутаций и обращений к GitHub нет |
| `3` | `not_ready` | — | захватывать нечего — прогон пропускается |
| `4` | `awaiting_merge` | — | открытый PR с подтверждённой готовностью; стоит `ai-awaiting-merge`; прогон пропускается, модели не запускаются |
| `4` | `work_exists` | — | PR найден, но `--adopt-existing` не передан; мутаций нет, решение за вызывающим |
| `5` | `readback_failed` | — | мутация выполнена, но подтвердить её не удалось — прогон пропускается, разбор по [recovery.md](recovery.md) |
| `6` | `source_unavailable` | — | источник недоступен — прогон пропускается; это не пустая очередь |
| `7` | `mutation_failed` | — | сам запрос изменения завершился ошибкой; readback не выполнялся |
| `2` | `usage` / `not_found` | — | неверный вызов или задачи нет — остановиться, исправить вызов |

**Без `claim` с кодом 0 implementation-воркер не запускается.** Пропущенный или неуспешный захват
означает ноль новых implementation-dispatch — это проверяемое условие, а не пожелание.
Код 0 с `mode: "review"` даёт ровно одно право: продолжить процесс на существующем PR.
Код 0 с `mode: "close"` — довести до конца закрытие уже влитого PR.

**`ai-blocked` останавливает захват раньше всего остального.** Эту метку ставит человек или
координатор при эскалации, и гейт, снимающий её самостоятельно, отменяет чужое решение.
Проверка выполняется сразу после чтения задачи — **до** поиска PR и до любой мутации:
задача с `ai-blocked` не захватывается ни в одном режиме, ни на реализацию, ни на ревью,
ни на закрытие, независимо от `ai-ready` и наличия PR. Ни одной метки гейт при этом не меняет
и ни одного обращения к GitHub не делает.

### Два режима вызова

`claim.js` вызывается в двух режимах, и разница между ними — **только** в обработке найденного PR.

* **Без `--adopt-existing`.** Найден PR по ключу задачи — команда возвращает код 4 `work_exists`
  и не трогает ни одной метки. Решение продолжать принимает вызывающий.
* **С `--adopt-existing`.** Это явное разрешение продолжить существующую работу: команда
  разбирает PR по состоянию и приводит метки в соответствие. **Автоматический маршрут обязан
  передавать этот флаг** — иначе задача с PR зависнет на коде 4 и до ревью не дойдёт никогда.

**Команда без флага не является read-only.** Обычный захват новой задачи — PR не найден, стоит
`ai-ready` — выполняет мутации в обоих режимах: снимает `ai-ready`, при `--transition-id` переводит
статус. «Ноль мутаций» верно ровно для трёх случаев: `blocked`, `not_ready` и `work_exists`.

### Три состояния существующего PR

Наличие PR само по себе ничего не решает. PR разбирается по **подтверждённой готовности**,
и состояний ровно три:

1. **Открытый PR без подтверждённой готовности** — `review_pending`. Это **работа**, а не ожидание:
   прогон запускается и продолжает процесс с той точки, где он остановился, — ревью Claude по текущему
   head, CI, обновление Jira. Метка `ai-awaiting-merge` не ставится.
2. **Открытый PR с подтверждённой готовностью** — `awaiting_merge`. Остался только merge, который
   выполняет человек. Прогон пропускается: **на каждом тике модели не запускаются**, задача стоит
   с меткой `ai-awaiting-merge` и ждёт.
3. **PR влит** — `closing`. Прогон идёт в режиме `close`: остаётся закрывающая часть процесса —
   статус, метки, запись в Jira. Новой реализации нет и здесь.

**Ни одно из трёх состояний не приводит к повторной реализации той же задачи.** Найден PR по ключу
задачи — координатор доводит до конца существующий. Новая ветка, новый PR и повторная реализация
запрещены при любом состоянии.

### Метки по состояниям

| Состояние | `ai-ready` | `ai-in-review` | `ai-awaiting-merge` |
|---|---|---|---|
| `claimed` | снимается | — | — |
| `review_pending` | снимается | **ставится** | снимается |
| `awaiting_merge` | снимается | снимается | **ставится** |
| `closing` | снимается | снимается | **сохраняется**, а если её нет — ставится |

**`ai-ready` при живом PR не остаётся** ни в одном из трёх случаев: иначе очередь выдаёт задачу
на каждом тике и работа выполняется заново.

Вместо `ai-ready` задача в состоянии `review_pending` несёт метку `ai-in-review` — и очередь её видит.
Это обязательное свойство: состояние, невидимое очереди, означает тихо потерянную задачу.
Продолжение начатой работы имеет приоритет над подхватом новой.

**`ai-awaiting-merge` при `closing` не снимается.** На этой метке держится обнаружение закрывающей
работы: `pickup.js` ищет задачи именно по ней, затем смотрит состояние PR и отличает ожидание merge
от закрытия после merge. Снять её при MERGED — значит потерять задачу в промежутке между merge
и Done. Для влитого PR метка означает не «готовность подтверждена», а «задача в зоне merge
и закрытия»; подтверждать там уже нечего — merge сделал человек.

**Набор меток отправляется без дублей и без пустых изменений.** Целевая метка, которая уже стоит,
не добавляется второй раз. Если после снятия и добавления набор совпадает с исходным, запрос
изменения не отправляется вовсе: записи в Jira на каждом тике без изменения состояния — лишний
расход и лишний риск. Readback при этом не нужен — подтверждать нечего.

**`ai-awaiting-merge` ставит только `claim.js`.** Проставлять эту метку вручную или другим
процессом запрещено: на ней держится допущение очереди о стадии задачи.

### Подтверждённая готовность

`awaiting_merge` объявляется **только** по подтверждённой готовности, и подтверждение проверяется
машинно, а не по впечатлению. Нужны оба условия сразу.

#### Условие 1 — вердикт Claude по текущему SHA

В Jira задачи есть комментарий с машинной строкой вердикта:

    AI-REVIEW-VERDICT: <ACCEPT|CHANGES_REQUIRED> sha=<40 hex> dispatch=<ctx_…> task=<task_…> run=<run_…>

* `sha` **посимвольно совпадает** с текущим head PR; сравнение регистронезависимое;
* присутствуют все три идентификатора — без них строка игнорируется целиком;
* автор комментария — **учётная запись, которой аутентифицирован сам гейт**. Комментарий любого
  другого автора не рассматривается: текст Jira недоверенный, и произвольная строка `ACCEPT`,
  написанная кем угодно, доказательством не является.

**Берётся последний вердикт по этому SHA, а не первый.** Комментарии перебираются в порядке Jira,
и решает последняя подходящая строка. Поэтому `CHANGES_REQUIRED`, написанный после `ACCEPT`
по тому же SHA, отменяет его — старый ACCEPT не перекрывает более поздний отрицательный вердикт.
Вердикт по другому SHA не учитывается вовсе: head сменился — вердикт недействителен.

**Разделение ответственности.** `claim.js` проверяет свойства самой записи: формат, наличие
идентификаторов, автора, совпадение SHA и то, что она последняя. Связь с реальным Claude-ревьюером
обеспечивает координатор: он пишет строку только после `worker_done` ревьюера, предварительно
сверив через `worker-show`, что dispatch завершился успешно, принадлежит этим `task`/`run` и agent —
claude. Идентификаторы в строке существуют ровно для того, чтобы эту связь можно было перепроверить
задним числом. Записывать строку авансом, по чужому вердикту или без SHA запрещено.

#### Условие 2 — обязательные проверки CI на том же SHA

Зелёным считается результат, в котором **каждая** обязательная проверка присутствует для этого SHA,
завершена (`status: completed`) и успешна (`conclusion: success`). Обязательные проверки —
`Tests (ubuntu-latest)` и `Tests (windows-latest)`; список переопределяется переменной окружения
`CLAIM_REQUIRED_CHECKS` только для тестов гейта.

Не считается зелёным ничто из перечисленного: проверка отсутствует в ответе; `queued` или
`in_progress`; `conclusion` равен `failure`, `cancelled`, `timed_out`, `action_required`, `neutral`,
`skipped` или `null`. **Отсутствующий, незавершённый и неизвестный результат — это не «зелёный».**
Логика «есть хотя бы одна успешная и нет провалов» запрещена **везде, где проверка разрешает
закрытие или объявляет готовность к merge**, — и в `claim.js`, и в `pickup.js`: она объявляет
готовность, пока CI ещё идёт. Требование одно и то же в обоих инструментах: все обязательные
проверки присутствуют, завершены и успешны **на том SHA, по которому принимается решение**
(head открытого PR для готовности, merge-коммит для закрытия). Разный набор обязательных
проверок у двух инструментов означал бы два разных определения «зелёного» — это запрещено.

Проверки ищутся по **полному** набору check-runs этого SHA. Ответ GitHub постраничный, и первая
страница не является всем набором: обязательная проверка, не попавшая в первую страницу, — это
не «проверка отсутствует». Гейт обходит страницы до конца либо запрашивает набор так, чтобы
получить его целиком.

**Недоступность CI — не «не зелёный».** Если запрос check-runs не выполнен (ненулевой код `gh`,
нечитаемый ответ), это отказ обязательного источника: код 6, ноль мутаций. Превращать такой
отказ в пустой список и далее в `ci: false` запрещено — результат неизвестен, а не отрицателен.

Невыполнение любого из двух условий — это `review_pending`, а не `awaiting_merge`.

**Что гейт сообщает о готовности.** В выводе `claim.js` объект `readiness` несёт три поля:
`verdictSha` — SHA решающего вердикта или `null`, если подходящего вердикта нет; `headSha` —
текущий head PR; `ci` — булево, истинное **только** когда все обязательные проверки прошли,
и `null`, когда проверка CI не выполнялась (вердикта не было, и спрашивать CI незачем).
`ci` — результат условия 2, а не итоговая готовность: итог виден по `state`.

### Мутации, readback и переходы

**Каждая мутация подтверждается перечитыванием.** После изменения меток задача читается заново,
и фактические метки сверяются с ожидаемыми: должны присутствовать целевые, отсутствовать снятые
и сохраниться все посторонние.

**Ошибка мутации и неподтверждённый readback — разные отказы, и путать их запрещено.**

* Сам запрос изменения завершился ошибкой — код `7`, `mutation_failed`. Readback при этом
  **не выполнялся**, и утверждать обратное гейт не имеет права.
* Запрос изменения прошёл, но перечитывание не подтвердило результат либо само не удалось —
  код `5`, `readback_failed`.

**Отказ мутации классифицируется по месту, а не по коду ошибки.** Единственное исключение —
`AUTH_FAILED`: прав на запись нет, это код `6` `source_unavailable`. **Любая другая** ошибка
запроса изменения — сетевая, `5xx`, `400`, разрыв соединения — это код `7`: мутация отправлена,
результат неизвестен, и состояние задачи в Jira не установлено. Это не то же самое, что
недоступный источник при чтении, и сводить их к одному коду запрещено: после кода `6` состояние
задачи заведомо прежнее, после кода `7` — неизвестно, и разбор по [recovery.md](recovery.md)
у них разный.

**Запрос перехода — такая же мутация, как смена меток**, и правило выше относится к нему целиком:
упавший `transition` — это код `7`, а не `readback_failed`. Перечитывания после него не было,
и называть отказ неподтверждённым readback значит сообщать о проверке, которая не выполнялась.

**Неверный вызов останавливает гейт, а не игнорируется.** Неизвестный флаг и флаг, у которого
нет значения, — ошибка использования, код `2`, ноль мутаций. Молчаливо пропущенный аргумент
означает запуск не с теми параметрами, которые задал вызывающий.

**`--repo` действует на все обращения к GitHub — и в `claim.js`, и в `pickup.js`.** Если репозиторий
задан, он связывает каждый вызов `gh`: флагом `--repo` там, где `gh` его принимает (`pr list`,
`pr view`), и путём эндпоинта `repos/<repo>/…` в `gh api`, у которого такого флага нет. Проверяется
связывание, а не буквальный флаг. Требование относится к обоим инструментам целиком: фильтрация
результата по репозиторию **после** выборки связыванием не является — выборка уже прошла не там.
Вызов, не связанный с репозиторием, зависит от текущего каталога, то есть результат зависит
от того, откуда его запустили.

**Переход статуса проверяется так же, как метки.** `--transition-id` передаётся только вместе
с `--expect-status <имя>`; вызов с одним `--transition-id` — ошибка использования, код `2`.
После перехода задача перечитывается, и фактический статус сравнивается с ожидаемым без учёта
регистра и крайних пробелов. Несовпадение — `readback_failed`. Переход, результат которого
не сверен, считается невыполненным.

### Сбой обязательного источника

Отказ обязательного источника — Jira, `gh` или CI — это **код 6**. Подменять его пустым
результатом, пустым списком или разрешением продолжить запрещено: неизвестный результат
не является ни «нет данных», ни «проверка не прошла».

Все данные, необходимые для решения, запрашиваются **до первой мутации**. Если источник
недоступен, гейт останавливается, не изменив ни меток, ни статуса.

Если отказ произошёл **после** уже выполненной мутации, частичное состояние фиксируется
явно: в выводе перечисляется, что успело измениться. Утверждать «мутаций не было» в этом
случае запрещено — это сообщение о проверке, которой не было.

### Поле `state` обязательно в каждом выводе

Таблица кодов возврата ключуется по `state`, и координатор читает именно его. Поэтому `state`
присутствует **в каждом** выводе `claim.js`, включая отказы, и совпадает с `reason`. Вывод,
в котором есть `reason`, но нет `state`, заставляет вызывающего угадывать состояние по коду
возврата — а один код возврата соответствует двум состояниям (`3` — это `blocked` или
`not_ready`, `4` — `awaiting_merge` или `work_exists`). Поле `success` остаётся булевым:
`true` только при коде `0`.

## Запуск воркеров

* Агент — `qwen-code`, **без** `--model`: модель и контекст резолвит сам Qwen, настройки не меняются.
* Каждый узел — отдельный new-child worktree.
* Одновременно не более **двух** независимых воркеров.
* Узлы, затрагивающие один файл, выполняются **последовательно**, а не параллельно.
* ТЗ передаётся по процедуре из [worker-contract.md](worker-contract.md): файл вне репозитория,
  чтение с сохранением завершающих переводов строк, один аргумент, readback сохранённого spec.
  Расхождение — воркер не запускается.

## Два канала ожидания

Ожидание результата и ожидание вопросов — **разные каналы**, и слушать нужно оба.

**Результат** — один блокирующий вызов на dispatch с конечным дедлайном:

    node tools/coordinator/settle.js watch --run <runId> --task <taskId> \
      --dispatch <dispatchId> --worktree <путь> --deadline-ms <N> > <лог вне репозитория> 2>&1

**Вопросы и эскалации** — ожидатель сообщений:

    orca orchestration check --wait --types "question,escalation" --timeout-ms <N> --json

**Ограничение, проверенное на практике: активный ожидатель у run может быть только один.** Второй
параллельный вызов немедленно отклоняется с `waiter_exists` и ничего не слушает. Поэтому держится
ровно один ожидатель на run, и он **перезапускается** после обработки каждой партии — иначе следующий
вопрос воркера останется без ответа.

Периодический опрос моделью запрещён в обоих каналах: ждут команды, а не повторные проверки.

## Вопросы воркеров

Вопрос приходит сообщением типа `question` и содержит Task и Dispatch ID. Порядок:

1. Ответ есть в ТЗ, брифе или уже принятом решении — ответить сразу: `orca orchestration reply --id <msg_id> --body "<ответ>"`.
2. Вопрос технический, но ответа нет — решает координатор и отвечает, фиксируя решение в журнале.
3. Вопрос архитектурный, затрагивает границы, безопасность или совместимость API — **эскалация к Claude
   до реализации**, работа воркера приостанавливается.
4. Вопрос продуктовый — к человеку, через Jira (см. ниже).

Неотвеченный `ask` воркера истекает по таймауту. Это **незавершённое ожидание**, а не отказ:
координатор перезапускает ожидатель и отвечает. Молчание ответом не считается.

## Когда беспокоить человека

Только через Jira — комментарием к задаче и меткой `ai-needs-input`, и только в трёх случаях:

* **продуктовое решение**: требование неоднозначно, и выбор меняет смысл результата;
* **недостающая авторизация**: нужен доступ, которого у контура нет;
* **действие, которое может выполнить только человек**: merge, подтверждение в UI, выдача токена.

Обычные технические развилки решает координатор или Claude. Интерактивные инструменты агента —
`ask_user_question` и подобные — каналом связи с человеком **не являются**: на них никто не отвечает,
и работа останавливается впустую. Вопрос, напечатанный в терминале, адресатом не имеет.

## Вызов Claude

Claude подключается в трёх точках: архитектурная неопределённость **до** реализации, независимое ревью
результата, сложное исключение. Для ревью Claude получает компактный пакет: цель, acceptance criteria,
точный SHA, diff, результаты проверок, риски и ссылки на полные данные вне репозитория. Обязательные
инструкции контура при этом не сокращаются.

Вызов — обычный supervised worker, агент `claude`:

    orca orchestration worker-start --spec-file <ТЗ ревью вне репозитория> \
      --task-title "<ключ задачи>: независимое ревью по SHA <sha>" \
      --worktree path:<рабочее дерево> --agent claude --run <runId>

Вердикт возвращается штатным `worker_done` и ждётся одним `check --wait` с конечным дедлайном.
ТЗ ревью обязано называть точный SHA и требовать `SHA_MISMATCH`, если фактический head PR отличается:
вердикт действителен только для проверенного коммита.

**Исключений по размеру изменения не бывает.** Однострочная правка документации проходит ревью так же,
как изменение продуктового кода. Оценка «изменение минимальное» решением координатора не является.

**Недоступность ревью — это `ai-blocked`, а не разрешение его пропустить.** Если Claude-воркер не
запускается, вердикт не приходит до дедлайна или возвращается `SHA_MISMATCH` — координатор ставит
`ai-blocked`, пишет в Jira фактическую причину с идентификаторами и останавливается. PR остаётся
открытым и к merge не предъявляется.

**Готовность к merge объявляется только после вердикта Claude по актуальному SHA.** Вердикт
фиксируется в Jira машинной строкой формата из раздела «Подтверждённая готовность» — её читает
`claim.js`, и без неё задача остаётся в состоянии `review_pending` сколько угодно тиков.
Отрицательный вердикт пишется той же строкой с `CHANGES_REQUIRED`: молчание после ревью
неотличимо от непроведённого ревью, а записанный отказ отменяет прежний ACCEPT по тому же SHA.

Отчёт воркера, зелёные тесты и успешный `worker_done` — **три разных свидетельства**. Ни одно не заменяет
остальные, и ни одно само по себе не является приёмкой.

## Проверки и гейты

Координатор не ослабляет ни один гейт ради зелёного результата:

* acceptance criteria формулируются **до** реализации и проверяемы;
* `node --test` и `git diff --check` запускаются координатором самостоятельно, отчёту воркера доверия нет;
* оба обязательных CI job должны быть зелёными на **точном итоговом SHA**; при смене head проверки
  повторяются на новом коммите;
* удаление, пропуск и ослабление тестов запрещены;
* после исправлений проверки и ревью выполняются заново.

**Бюджет исправлений — две итерации на задачу.** Он считается по задаче, а не по сессии: новая сессия,
новый Task или перезапуск координатора его не обнуляют. Исчерпан — метка `ai-blocked` и эскалация человеку.

## Запреты координатора

* Не выполнять merge, не переключать и не изменять `master`.
* Не использовать `push --force`, `reset --hard`, `git stash`, `git clean`, `git checkout -- <путь>`.
* Не отбрасывать чужие незакоммиченные изменения.
* Не изменять `CLAUDE.md`, `QWEN.md`, `AGENTS.md`, `docs/**` — это зона Claude.
* Не писать продуктовый код и тесты самому.
* Не изменять настройки агентов, права, способ оплаты и конфигурацию авторизации.
* Не выводить секреты: токены, ключи, заголовки авторизации, содержимое файлов учётных данных.
* Не брать более одной задачи и не запускать более двух воркеров одновременно.
* Не включать расписания и автоматизации без явного решения человека.

## Завершение и честность состояния

Неоднозначность, недоступность источника и истёкший дедлайн **успехом не считаются**. Любое из них —
остановка с записью причины в журнал, а при необходимости `ai-blocked` и эскалация.

Перед завершением прогона: все dispatch доведены до settlement, партии сообщений подтверждены,
терминалы освобождены либо честно отмечена причина удержания, блокировка координатора снята.
